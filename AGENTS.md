# AGENTS.md

Правила того, **как Codex должен вести разработку**. Файл intentionally generic: описывает процесс и артефакты проекта, а не конкретное ТЗ/задачу.

## Основные принципы

- Работай итеративно: маленькие изменения → проверка → фиксация результата.
- Фокус на поддерживаемости: простые решения, минимум “магии”, явные контракты.
- Всегда сохраняй историю: код + документация + чейнджлог + трекинг задач должны соответствовать друг другу.
- Если требований/контекста недостаточно — сначала уточни, затем реализуй.
- Когда закончишь работу скомпилируй и попытайся установить то что сделал.
- Пиши так, чтобы следующий разработчик (включая тебя самого через 3 месяца) мог быстро понять что и почему было сделано.
- Отвечай на русском языке, если не оговорено иное.

## Обязательные артефакты репозитория

Поддерживай эти файлы в актуальном состоянии (создавай, если их нет):
- `README.md` — что это за проект, как установить/запустить/проверить, основные команды, ограничения.
- `CHANGELOG.md` — журнал изменений (Keep a Changelog), раздел **Unreleased** обязателен.
- `ROADMAP.md` — краткий план развития (вехи/релизы/приоритеты).
- `task.json` — список задач/бэклог проекта в машиночитаемом виде (см. формат ниже).
- `docs/` — документация по архитектуре/решениям (по мере роста проекта).

## `task.json` (бэклог): формат и правила

Держи `task.json` в корне репозитория. Формат — JSON‑массив объектов задач:
- обязательные поля: `id`, `title`, `status`
- рекомендуемые поля: `priority`, `area`, `owner`, `estimate`, `dependsOn`, `notes`, `createdAt`, `updatedAt`

Правила ведения:
- `id` — стабильный (не переиспользовать).
- `status` — один из: `todo`, `in_progress`, `blocked`, `done`, `canceled`.
- Любой PR/итерация должен обновлять статус соответствующих задач и/или добавлять новые задачи, если они обнаружены в процессе.
- В `ROADMAP.md` отражай крупные вехи, а в `task.json` — конкретные задачи.

## CHANGELOG: как вести

- Следуй Keep a Changelog: `Added`, `Changed`, `Fixed`, `Removed`, `Security`.
- Любое заметное изменение поведения/публичного API/UX должно попадать в `CHANGELOG.md` (в **Unreleased**).
- Записи должны быть короткими, ориентированными на пользователя/интегратора (что изменилось и зачем).

## README: минимальные требования

`README.md` должен содержать:
- краткое описание проекта и его назначение;
- требования окружения (версии runtime/инструментов);
- команды разработки (build/test/lint/run);
- как проверить изменения (локально, шаги воспроизведения);
- ссылки на `CHANGELOG.md`, `ROADMAP.md`, `task.json`.

## Архитектура и документация решений

Если решение влияет на расширяемость/поддержку (например: выбранная модель состояния, протоколы, формат данных, правила миграций):
- зафиксируй короткий ADR в `docs/adr/NNNN-title.md` (контекст → решение → последствия).

Не заводи ADR на тривиальные правки.

## Git‑процесс

- Делай маленькие осмысленные коммиты; не “комбайнь” несвязанные изменения.
- Сообщения коммитов: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`).
- Отдельно коммить: форматирование/рефакторинг/фичи/тесты/документацию (когда это возможно без лишней дробности).
- Когда работа готова к проверке — создай Pull Request (или аналог) с описанием изменений и ссылками на задачи из `task.json`.

## Версионирование и релизы

- Используй SemVer, если проект публикуется; иначе всё равно поддерживай понятные версии для “срезов” состояния.
- Перед релизом: обнови `CHANGELOG.md` (вынеси из **Unreleased** в версию), обнови версию в манифесте/метаданных проекта, убедись что сборка/тесты зелёные.
- Релиз должен быть воспроизводимым: фиксируй lockfile и не публикуй из “грязного” рабочего дерева.
- Сам предлагай релизы, когда накопилось достаточно изменений.
- Релизы должны быть оформлены тегами в git (например, `v1.2.3`).
- Релизы храни в GitHub Releases или аналоге (если есть).
- Файлы релизов храни в /out

## Качество и проверки

Перед завершением работы (и перед релизом) соблюдай “quality gates” проекта:
- сборка проходит;
- линт/форматирование соблюдены (если настроены в проекте);
- тесты проходят (если есть);
- документация обновлена (`README.md`, `CHANGELOG.md`, при необходимости `ROADMAP.md`/`task.json`).

Если в репозитории пока нет тестов/линта, то при bootstrap добавь минимум:
- единый способ запуска сборки;
- единый способ запуска тестов (хотя бы для “чистой” логики);
- единый способ запуска линтера/форматтера (если это уместно для стека).

## Зависимости

- Добавляй зависимости только при явной необходимости; предпочитай стандартную библиотеку и уже используемые пакеты.
- Не обновляй зависимости “просто так” вместе с функциональными изменениями; делай это отдельным коммитом/PR.
- Держи lockfile в репозитории (если используется в выбранном экосистемном менеджере).
- Фиксируй версии

## Безопасность и приватность

- Не добавляй телеметрию и сетевые запросы без явного требования.
- Не коммить секреты (ключи, токены, приватные URL), используй gitignore. Если обнаружены — удаляй из истории проекта безопасным способом и фиксируй в `CHANGELOG.md` при необходимости.
- Минимизируй права и побочные эффекты: не меняй окружение пользователя без необходимости.

## Definition of Done (общий)

Работа считается завершённой, когда:
- код соответствует текущим задачам/требованиям и не ломает существующее поведение;
- пройдены проверки (build/lint/test) или явно описано, что именно отсутствует и почему;
- `README.md`/`CHANGELOG.md` актуальны;
- `task.json` и `ROADMAP.md` отражают фактическое состояние проекта.
